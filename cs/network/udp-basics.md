# [실습 2] UDP — TCP와 비교하며 보기

> **이 실습은 TCP 복습을 겸한다.** 매 단계에서 "TCP는 어땠더라?" 를 먼저 떠올릴 것.

---

# 1부. 한 장으로 보는 차이

```
 ┌───────────────── TCP ─────────────────┐   ┌──────────── UDP ────────────┐
 │                                       │   │                             │
 │  ① SYN      ──────▶                   │   │   (연결 수립 없음)            │
 │  ② SYN+ACK  ◀──────                   │   │                             │
 │  ③ ACK      ──────▶                   │   │                             │
 │  ═══ 통로 완성 ═══                     │   │   데이터 ──────▶  그게 끝     │
 │                                       │   │                             │
 │  데이터 ──────▶                        │   │   데이터 ──────▶             │
 │  ACK   ◀──────   "받았다"              │   │        (확인 없음)           │
 │  데이터 ──────▶                        │   │   데이터 ──────▶             │
 │  ACK   ◀──────                        │   │        (확인 없음)           │
 │                                       │   │                             │
 │  FIN/ACK/FIN/ACK  종료                 │   │   (종료 절차 없음)           │
 └───────────────────────────────────────┘   └─────────────────────────────┘
```

| | **TCP** | **UDP** |
|---|---|---|
| 연결 | **3-way handshake** | **없음** |
| 도착 보장 | ✅ ACK + 재전송 | ❌ 보내고 끝 |
| 순서 보장 | ✅ 순서번호로 재조립 | ❌ 뒤섞일 수 있음 |
| 중복 제거 | ✅ | ❌ |
| 흐름/혼잡 제어 | ✅ | ❌ |
| 속도 | 느림 | **빠름** |
| **헤더 크기** | **20 bytes** | **8 bytes** |
| 연결 상태 | `LISTEN` / `ESTABLISHED` / `TIME_WAIT` | **상태 없음** |
| Java 클래스 | `ServerSocket` + `Socket` | **`DatagramSocket` 하나** |

## ⭐ 헤더를 보면 "왜 기능이 없는지" 가 보인다

```
 TCP 헤더 (20 bytes)                    UDP 헤더 (8 bytes)
 ┌─────────────┬─────────────┐         ┌─────────────┬─────────────┐
 │  출발 포트   │  도착 포트   │         │  출발 포트   │  도착 포트   │
 ├─────────────┴─────────────┤         ├─────────────┼─────────────┤
 │      순서번호 (seq)        │         │    길이      │   체크섬     │
 ├───────────────────────────┤         └─────────────┴─────────────┘
 │      확인번호 (ack)        │
 ├──────┬────────────────────┤          seq 도 ack 도 없다
 │ 플래그 │   윈도우 크기       │          → 순서를 맞출 수도
 ├──────┴────────────────────┤             재전송을 할 수도 없다
 │   체크섬    │  긴급 포인터  │          기능이 없는 게 아니라
 └─────────────┴─────────────┘          애초에 적을 칸이 없다
```

**UDP가 "기능을 뺀" 게 아니라, 처음부터 그런 칸을 만들지 않은 것이다.**
그래서 **헤더가 작고 빠르다.**

# 2부. 코드로 보는 차이

```java
// ───── TCP ─────                      // ───── UDP ─────
ServerSocket server =                   DatagramSocket socket =
    new ServerSocket(9000);                 new DatagramSocket(9001);
                                        //  클래스가 하나뿐이다
Socket client = server.accept();        //  accept() 가 없다
//  연결을 기다린다                      //  연결이라는 개념이 없으니까

client.getInputStream()                 DatagramPacket p = new DatagramPacket(buf, len);
       .read(...)                       socket.receive(p);
//  "연결된 상대" 와 주고받는다            //  "패킷 하나" 를 받는다. 누가 보냈든

                                        p.getAddress();  p.getPort();
//  상대를 기억한다                      //  ⚠️ 상대 주소를 패킷에서 꺼내야 한다
                                        //     연결이 없으니 기억하지 않는다
```

**세 가지 차이가 코드에 그대로 드러난다.**

| | TCP | UDP |
|---|---|---|
| 클래스 | `ServerSocket` + `Socket` 2개 | `DatagramSocket` **1개** |
| 연결 대기 | `accept()` | **없음** — 바로 `receive()` |
| 상대 주소 | 소켓이 기억 | **패킷에서 꺼낸다** |

> **"상대를 기억하지 않는다"** 가 UDP 의 본질이다.
> 매 패킷이 독립적인 편지다. 앞뒤 맥락이 없다.

**터미널 2**

**터미널 3**
```bash
nc -u 127.0.0.1 9001          # -u 가 UDP 옵션
```
→ 아무것도 안 일어난다. **접속해도 패킷이 하나도 안 나간다.**

이제 `hello` 를 치고 엔터.

```
IP 127.0.0.1.52341 > 127.0.0.1.9001: UDP, length 6      ← 데이터가 바로 간다
IP 127.0.0.1.9001 > 127.0.0.1.52341: UDP, length 13     ← 응답
```

### 🔍 TCP와 비교해보라

| | TCP | UDP |
|---|---|---|
| 접속했을 때 | `[S]` `[S.]` `[.]` 3줄 | **아무것도 없음** |
| `hello` 보냈을 때 | `[P.]` `[.]` `[P.]` `[.]` 4줄 | **`UDP` 2줄** |
| 플래그 표시 | `[S]` `[P.]` `[F.]` ... | **없음** |

**`Flags` 자체가 안 나온다.** UDP 헤더에 플래그 칸이 없기 때문이다.

## Step 2. 연결 상태가 없다

```bash
netstat -an | grep 9001
```
```
udp4   0   0   *.9001   *.*
                         └─ 상태 칸이 비어 있다
```

**`LISTEN` 도 `ESTABLISHED` 도 `TIME_WAIT` 도 없다.**
연결이 없으니 **연결 상태라는 것도 없다.**

> TCP 는 `netstat` 에 연결마다 줄이 생겼다. UDP 는 **접속자가 몇 명이든 한 줄**이다.

## Step 3. ⭐ 서버가 꺼져 있어도 "성공" 한다

**터미널 1의 서버를 `Ctrl+C` 로 끄고**, 터미널 3에서:

```bash
nc -u 127.0.0.1 9001
hello
```
→ **아무 에러도 안 난다.** 그냥 조용하다.

### TCP였다면?
```bash
nc 127.0.0.1 9000        # 서버 꺼진 상태
```
```
nc: connectx to 127.0.0.1 port 9000 failed: Connection refused
```
**즉시 거부당한다.** 서버가 `RST` 를 보내기 때문이다.

```
 TCP   연결을 먼저 맺으므로  →  상대가 없으면 "그 자리에서" 안다
 UDP   그냥 던지므로        →  상대가 있는지조차 모른다
```

**이게 "비연결형(connectionless)" 의 의미다.**

## Step 4. 패킷 유실 재현

```bash
java UdpLossTest.java 30000
```

실제 결과:
```
┌──────────────────────────────────────┐
│  보낸 패킷   :     30,000            │
│  받은 패킷   :     29,260            │
│  유실        :        740  (2.47%)   │
│  전송 소요   :        107 ms         │
└──────────────────────────────────────┘

유실된 번호 예시: 5384 5385 5388 7240 7242 7243 ...
```

**`send()` 는 30,000번 모두 성공했다. 그런데 도착한 건 29,260개다.**

### 왜 유실됐나 — 같은 컴퓨터 안인데?

```
   보내는 쪽                     받는 쪽
   30,000개를 107ms 에  ──────▶  수신 버퍼 (8KB)
   쏟아붓는다                        │
                                    │ 앱이 하나씩 꺼내 처리
                                    ▼
                              처리 속도 < 도착 속도
                                    │
                              버퍼가 가득 참
                                    │
                              💥 넘치는 패킷은 그냥 버린다
```

**TCP라면?** 흐름 제어(`win` 필드)가 있어서 **"나 지금 버퍼 꽉 찼으니 천천히 보내"** 라고 알린다.
보내는 쪽이 속도를 줄인다. **UDP 에는 그런 칸이 없다.**

> 실제 네트워크에서는 **라우터 혼잡, 전파 간섭** 등으로 유실이 더 잘 일어난다.
> loopback 에서도 2%가 사라진다는 건 꽤 충격적이다.

# 4부. 그럼 UDP 는 왜 쓰나

**"나쁜 TCP" 가 아니다. 다른 트레이드오프다.**

| 쓰는 곳 | 왜 |
|---|---|
| **DNS** | 질의 하나가 작고 빠르다. 실패하면 **그냥 다시 물으면 된다.** handshake 비용이 아깝다 |
| **영상·음성 스트리밍** | 지난 프레임을 **재전송받아봐야 이미 늦었다.** 끊기더라도 최신 프레임이 낫다 |
| **온라인 게임** | **최신 좌표**만 중요하다. 3초 전 위치를 재전송받을 이유가 없다 |
| **QUIC / HTTP3** | UDP 위에 **신뢰성을 직접 구현**한다 (아래 참고) |

```
 영상 통화에서 패킷 하나가 유실되면?

 [TCP 방식]   재전송을 기다린다 → 화면이 멈춘다 → 복구되면 과거 장면부터 재생 😖
 [UDP 방식]   그냥 건너뛴다    → 잠깐 깨지고 계속 진행                      😊
```

**"늦게라도 정확히" vs "조금 틀려도 지금"** 의 선택이다.

## 💡 HTTP/3 는 왜 UDP 를 쓸까

```
 HTTP/2 (TCP 위)              HTTP/3 (UDP 위, QUIC)
   TCP handshake   3-way        ┐
   TLS handshake   추가 왕복     ┘  둘을 합쳐 1번으로 줄임
```
**TCP의 연결 수립이 느려서**, UDP 위에 **필요한 신뢰성만 직접 구현**한 것이 QUIC 이다.
"TCP는 느리다"는 문제를 **프로토콜을 갈아타서** 해결한 사례다.

# 면접 포인트

1. **TCP와 UDP의 차이는?**
   → TCP 는 **연결형**이고 **3-way handshake** 로 통로를 만든 뒤, **ACK와 재전송**으로 도착을,
   **순서번호**로 순서를 보장한다. UDP 는 **비연결형**이고 그런 장치가 없어서 **빠르지만
   유실·순서 뒤바뀜이 발생**할 수 있다.

2. **UDP는 왜 쓰나요?**
   → **재전송이 의미 없는 경우** 때문이다. 영상·음성·게임은 **지난 데이터를 복구해봐야 이미 늦다.**
   DNS 처럼 질의가 짧으면 handshake 비용이 더 크다.

3. **UDP가 빠른 이유는?**
   → ① handshake 가 없어 **첫 데이터까지 왕복이 0번** ② 헤더가 **8바이트**(TCP는 20)
   ③ ACK·재전송·흐름 제어 같은 **부가 처리가 없다**

4. **UDP로 신뢰성이 필요하면?**
   → **애플리케이션 레벨에서 직접 구현**한다. **QUIC(HTTP/3)** 이 그렇게 만들어졌다.
   TCP 의 연결 수립 지연을 줄이려고 UDP 위에 필요한 기능만 얹었다.

5. **흐름 제어와 혼잡 제어는?**
   → **흐름 제어**는 수신자 버퍼가 넘치지 않게(TCP 헤더의 `win` 필드),
   **혼잡 제어**는 네트워크가 막히지 않게 속도를 조절하는 것. **둘 다 UDP 에는 없다.**
   그래서 실습에서 수신 버퍼가 넘쳐 패킷이 버려졌다.

# 6부. "UDP를 왜 쓰나" 를 그림으로

## 판단 기준은 두 개다

```
 ① "늦게 도착한 데이터가 아직 쓸모 있는가?"
       있다  →  TCP   (파일, 웹페이지, DB, 결제)
       없다  →  UDP   (실시간 영상, 음성, 게임)

 ② "주고받을 양이 연결 비용보다 큰가?"
       크다  →  TCP   (파일 다운로드)
       작다  →  UDP   (DNS 질의 한 번)
```

---

## Case 1. 영상 통화 — **늦은 프레임은 쓸모가 없다**

### TCP 로 하면

```
 보낸 프레임   1    2    3    4    5    6    7
 도착         ✓    ✓    ✗    ✓    ✓    ✓    ✓
                        유실

 TCP 수신 버퍼            [4][5][6][7]  ← 도착해 있는데
                                          3번이 없어서 못 올려보냄

 화면         1    2    ███ 멈춤 ███    3    4    5    6    7
                        └── 재전송 기다리는 동안 ──┘
                            4,5,6,7 도 같이 막힌다
```

**이걸 head-of-line blocking(줄 맨 앞이 막힘) 이라고 한다.**
TCP 는 **순서를 보장**하므로, 앞의 하나가 빠지면 **뒤가 다 도착해 있어도** 전달하지 않는다.

> 화장실 한 칸에 줄 선 사람들. 맨 앞 사람이 안 나오면 **뒤는 전부 기다린다.**

**체감:** 영상이 멈췄다가, 복구되면 **과거 장면부터** 몰아서 재생된다 → **지연이 계속 쌓인다.**

### UDP 로 하면

```
 보낸 프레임   1    2    3    4    5    6    7
 도착         ✓    ✓    ✗    ✓    ✓    ✓    ✓

 화면         1    2   (깨짐)  4    5    6    7
                       └ 잠깐 지직거리고 바로 다음 프레임
```

**체감:** 한 번 깨지지만 **항상 "지금" 을 보여준다.** 지연이 안 쌓인다.

```
 영상 통화에서 1초 전 화면을 완벽하게 복구해주는 게 의미가 있나?
                        없다.
```

## Case 2. 온라인 게임 — **최신 좌표만 의미가 있다**

캐릭터 위치를 초당 60번 보낸다고 하자.

```
  t=0ms    위치 (10, 20)   ✓ 도착
  t=16ms   위치 (12, 21)   ✗ 유실
  t=32ms   위치 (15, 23)   ✓ 도착
  t=48ms   위치 (18, 26)   ✓ 도착
```

### TCP

```
  16ms 패킷 유실 감지 → 재전송 요청 → 50ms 뒤 도착

  그동안 32ms, 48ms 패킷은 버퍼에서 대기 (head-of-line blocking)

  t=66ms  드디어 "50ms 전에 (12,21) 에 있었습니다" 수신
                       ▲
          지금 와서 알아봐야 무슨 소용인가?
          그리고 그 사이 최신 위치들도 막혀 있었다

  → 캐릭터가 순간이동(렉)하는 것처럼 보인다
```

### UDP

```
  16ms 유실 → 그냥 버린다
  32ms 의 (15, 23) 을 즉시 사용

  → 좌표 하나 건너뛰었을 뿐. 화면은 부드럽게 이어진다
```

**과거 위치를 복구하는 건 가치가 0 이다.** 어차피 캐릭터는 이미 다른 곳에 있다.

## Case 3. DNS — **배보다 배꼽이 크다**

```
 질의:  "naver.com 의 IP 가 뭐야?"     약 30 bytes
 응답:  "223.130.200.107"              약 50 bytes
                                       ───────────
                                       실제 데이터 80 bytes
```

### TCP 로 한다면

```
  ① SYN              ──────▶  ┐
  ② SYN+ACK          ◀──────  ├ 왕복 1   연결 수립
  ③ ACK              ──────▶  ┘
  ④ 질의 (30B)        ──────▶  ┐
  ⑤ ACK              ◀──────  ├ 왕복 2   실제 용건
  ⑥ 응답 (50B)        ◀──────  │
  ⑦ ACK              ──────▶  ┘
  ⑧ FIN              ──────▶  ┐
  ⑨ ACK              ◀──────  ├ 왕복 3~4  종료
  ⑩ FIN              ◀──────  │
  ⑪ ACK              ──────▶  ┘

  패킷 11개 · 왕복 4회 · TCP 헤더만 11 × 20 = 220 bytes
```

### UDP

```
  ① 질의 (30B)        ──────▶  ┐
  ② 응답 (50B)        ◀──────  ┘ 왕복 1

  패킷 2개 · 왕복 1회 · UDP 헤더 2 × 8 = 16 bytes
```

### 나란히 비교

| | TCP | UDP |
|---|---|---|
| 패킷 수 | **11개** | **2개** |
| 왕복 횟수 | **4회** | **1회** |
| 헤더 낭비 | **220 bytes** | **16 bytes** |
| 실제 데이터 | 80 bytes | 80 bytes |

**80바이트를 주고받으려고 220바이트의 포장지를 쓰는 셈이다.**

### "유실되면 어떡하나?" → **그냥 다시 물으면 된다**

```
  질의 ──X  (유실)
  ...1초 기다려도 응답이 없네?
  질의 ──────▶  재질의

  재질의 비용(패킷 2개) < handshake 비용(패킷 9개)
```

**애플리케이션이 직접 재시도하는 게 TCP 를 쓰는 것보다 싸다.**

> 실제로 DNS 응답이 512 bytes 를 넘으면 **TCP 로 전환**한다.
> 데이터가 커지면 그때는 TCP 가 더 이득이기 때문이다. **상황에 맞게 고르는 것.**

## 정리

| | 무엇이 중요한가 | 프로토콜 |
|---|---|---|
| 파일 다운로드 | **정확성.** 1바이트만 틀려도 파일이 깨진다 | **TCP** |
| 웹페이지 / REST API | **정확성.** JSON 이 잘리면 파싱 실패 | **TCP** |
| 결제 / DB | **정확성.** 두말할 것 없다 | **TCP** |
| 영상 · 음성 통화 | **실시간성.** 늦은 프레임은 쓸모없다 | **UDP** |
| 온라인 게임 | **실시간성.** 최신 좌표만 의미 있다 | **UDP** |
| DNS | **가벼움.** 연결 비용이 데이터보다 크다 | **UDP** |

```
          "늦게라도 정확히"        vs       "조금 틀려도 지금"
                TCP                             UDP
```

## 💡 HTTP/3 가 UDP 로 간 이유도 여기 있다

```
 HTTP/1.1, HTTP/2  (TCP 위)
    한 연결로 여러 파일을 받는데, 패킷 하나가 유실되면
    → head-of-line blocking → 관련 없는 파일들까지 전부 대기 💥

 HTTP/3 (QUIC = UDP 위)
    스트림마다 독립적으로 처리 → 하나가 막혀도 나머지는 진행
    + TCP handshake 와 TLS handshake 를 합쳐 왕복 횟수를 줄임
```

**"TCP 의 순서 보장이 오히려 방해가 되는" 상황**이 있다는 걸 보여주는 사례다.
UDP 위에 **필요한 신뢰성만 직접 구현**한 것이 QUIC 이다.
