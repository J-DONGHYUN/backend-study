# 1부. 개념

## 1-1. IP 와 포트 — 왜 둘 다 필요한가

```
   IP 주소                  포트 번호
   "어느 컴퓨터냐"            "그 컴퓨터의 어느 프로그램이냐"

   192.168.0.5       :        9000
   └─ 건물 주소 ─┘           └ 호실 번호 ┘
```

한 컴퓨터에서는 **여러 프로그램이 동시에** 네트워크를 쓴다.

```
  내 노트북 (127.0.0.1)
     ├─ 포트 8080 → Spring Boot
     ├─ 포트 3306 → MySQL
     ├─ 포트 9000 → 우리 에코 서버
     └─ 포트 5432 → PostgreSQL
```

**IP만으로는 "어느 프로그램에 전달할지" 알 수 없다.** 그래서 포트가 필요하다.

| 포트 범위 | 용도 |
|---|---|
| 0 ~ 1023 | **well-known.** 22(SSH), 80(HTTP), 443(HTTPS). 보통 관리자 권한 필요 |
| 1024 ~ 49151 | 등록 포트. 3306(MySQL), 8080(웹 개발) |
| 49152 ~ 65535 | **임시 포트.** 클라이언트가 접속할 때 OS가 자동으로 하나 빌려준다 |

> 실습에서 `nc` 로 접속하면 클라이언트 포트가 `61105` 같은 큰 숫자인 걸 보게 된다.
> **내가 정한 게 아니라 OS 가 비어있는 걸 골라준 것**이다.

## 1-2. 소켓 — 통신의 양쪽 끝

**소켓 = IP + 포트.** 통신선의 한쪽 끝이다.

```
   클라이언트                                    서버
 ┌─────────────┐                          ┌─────────────┐
 │ 127.0.0.1   │ ◀──────── 연결 ───────▶  │ 127.0.0.1   │
 │   :61105    │                          │   :9000     │
 └─────────────┘                          └─────────────┘
    소켓 A                                    소켓 B
```

**연결 하나는 네 개의 값으로 구분된다.**

```
( 출발 IP , 출발 포트 , 도착 IP , 도착 포트 )
( 127.0.0.1, 61105   , 127.0.0.1, 9000    )
```

그래서 **같은 서버 포트(9000)에 여러 명이 동시에 접속해도** 섞이지 않는다.
클라이언트 포트가 다르기 때문이다.

```
 손님1  127.0.0.1:61105  ──┐
 손님2  127.0.0.1:61106  ──┼──▶  서버 127.0.0.1:9000
 손님3  127.0.0.1:61107  ──┘
        └ 포트가 다르니 구분된다
```

## 1-3. TCP 연결 = 3-way handshake

TCP는 **연결을 먼저 수립하고** 데이터를 주고받는다. (전화와 비슷하다)

```
  클라이언트                                        서버
      │                                             │
      │                                     [LISTEN] 대기 중
      │                                             │
      │  ①  SYN                                     │
      │     "연결하고 싶어. 내 순서번호는 x 야"        │
      │  ─────────────────────────────────────────▶ │
      │                                             │  [SYN_RECEIVED]
      │  ②  SYN + ACK                               │
      │     "좋아. 네 x 받았어(ACK).                  │
      │      내 순서번호는 y 야(SYN)"                 │
      │  ◀───────────────────────────────────────── │
      │                                             │
 [ESTABLISHED]                                      │
      │  ③  ACK                                     │
      │     "네 y 받았어"                            │
      │  ─────────────────────────────────────────▶ │
      │                                       [ESTABLISHED]
      │                                             │
      │ ══════════ 이제 데이터를 주고받는다 ═══════════ │
```

### 왜 하필 3번인가

**양쪽 모두 "보내기"와 "받기"가 둘 다 되는지 확인해야** 하기 때문이다.

```
 ① 이 끝나면   서버는 안다 : "클라이언트→서버 통신 OK"
 ② 가 끝나면   클라이언트는 안다 : "서버→클라이언트 통신 OK"
 ③ 이 끝나면   서버는 안다 : "내 응답이 잘 도착했구나"
```

- **2번이면?** 서버가 ②를 보낸 뒤, 그게 도착했는지 **알 수 없다.**
- **4번이면?** ②와 ③을 합칠 수 있는데 굳이 나누는 건 낭비다.

> **면접 단골:** "왜 3-way 인가요?" → **양방향 통신이 모두 가능함을 서로 확인하기 위해서.**
> 2번이면 서버가 자기 패킷의 도착을 확인하지 못한다.

## 1-4. 연결 종료 = 4-way handshake

```
  클라이언트                                        서버
      │  ①  FIN   "나는 보낼 거 다 보냈어"            │
      │  ─────────────────────────────────────────▶ │
      │                                       [CLOSE_WAIT]
      │  ②  ACK   "알겠어"                           │
      │  ◀───────────────────────────────────────── │
      │                                             │
      │        ⚠️ 여기서 서버는 아직 보낼 게 남았을 수 있다
      │           (그래서 ②와 ③이 합쳐지지 않는다)     │
      │                                             │
      │  ③  FIN   "나도 다 보냈어"                   │
      │  ◀───────────────────────────────────────── │
      │                                        [LAST_ACK]
      │  ④  ACK   "알겠어"                           │
      │  ─────────────────────────────────────────▶ │
 [TIME_WAIT]                                   [CLOSED]
      │
      │  ... 일정 시간 대기 후 ...
 [CLOSED]
```

**연결은 3번인데 종료는 왜 4번인가?**
→ TCP 연결은 **양방향**이라 **각 방향을 따로 닫아야** 한다.
내가 끊고 싶어도 **상대는 아직 보낼 게 남았을 수 있다.**

## 1-5. `TIME_WAIT` — 왜 바로 안 닫나

**먼저 끊은 쪽**이 잠시(보통 수십 초) 머무는 상태. 이유는 둘이다.

```
 ① 마지막 ACK 가 유실되면?
       클라이언트 ──④ ACK──X  (유실)
                              서버: "응답이 없네?" → FIN 재전송
       이때 받아줄 사람이 필요하다.
       이미 CLOSED 면 RST(연결 거부)를 보내게 되고 서버는 비정상 종료로 인식한다

 ② 늦게 도착한 패킷이 섞이는 걸 막는다
       같은 포트로 새 연결이 생겼을 때,
       이전 연결의 늦은 패킷이 새 연결 데이터로 오인될 수 있다
```

> **실무 이슈:** 트래픽이 많은 서버는 `TIME_WAIT` 소켓이 수만 개 쌓여 **포트가 고갈**될 수 있다.
> 면접에서 "`TIME_WAIT` 이 왜 생기고 많으면 어떤 문제가 있나요?" 로 나온다.

## 1-6. 상태 한눈에

```
  서버                                  클라이언트

  CLOSED                                CLOSED
    │ ServerSocket 생성                   │
    ▼                                     │
  LISTEN   ◀── 연결 요청 대기              │ connect()
    │                                     ▼
    │ SYN 수신                           SYN_SENT
    ▼                                     │
  SYN_RECEIVED                            │
    │ ACK 수신                            ▼
    ▼                                  ESTABLISHED
  ESTABLISHED ◀════ 데이터 송수신 ════▶
    │                                     │ close()
    │ FIN 수신                            ▼
    ▼                                  FIN_WAIT
  CLOSE_WAIT                              │
    │ close()                             │
    ▼                                     ▼
  LAST_ACK                             TIME_WAIT
    │                                     │ (대기)
    ▼                                     ▼
  CLOSED                                CLOSED
```

## Step 1. 서버 띄우고 LISTEN 확인

**터미널 1**

java TcpEchoServer.java

**터미널 3**

## Step 2. tcpdump 켜기

**터미널 2**
```bash
sudo tcpdump -i lo0 -n 'tcp port 9000'
```

| 옵션 | 뜻 |
|---|---|
| `-i lo0` | **loopback 인터페이스.** 내 컴퓨터 안에서만 오가는 트래픽 |
| `-n` | 이름 대신 **숫자 주소**로 표시 (빠르고 읽기 쉬움) |
| `'tcp port 9000'` | 9000 포트 트래픽만 |

비밀번호를 물으면 입력한다. (패킷 캡처는 관리자 권한이 필요)

```
tcpdump: listening on lo0, ...
```
이 상태로 **그대로 두고** 다음 단계로 간다.

## Step 3. 접속 — 여기서 handshake 가 찍힌다 ⭐

**터미널 3**
```bash
nc 127.0.0.1 9000
```

→ **터미널 2 를 보라.** 이런 게 세 줄 나타난다.

```
IP 127.0.0.1.61105 > 127.0.0.1.9000: Flags [S],  seq 1234567890, ...
IP 127.0.0.1.9000 > 127.0.0.1.61105: Flags [S.], seq 987654321, ack 1234567891, ...
IP 127.0.0.1.61105 > 127.0.0.1.9000: Flags [.],  ack 1, ...
```

### tcpdump 한 줄 읽는 법

```
IP 127.0.0.1.61105 > 127.0.0.1.9000: Flags [S], seq 1234567890, win 65535
   └─── 출발 ────┘   └─── 도착 ───┘        │          │
        IP.포트          IP.포트          플래그    순서번호
```

### Flags 표 — 이것만 알면 된다

| 표시 | 의미 | 언제 |
|---|---|---|
| `[S]` | **SYN** | ① 연결 요청 |
| `[S.]` | **SYN + ACK** | ② 연결 수락 (`.` 이 ACK) |
| `[.]` | **ACK** | ③ 확인 응답 |
| `[P.]` | **PSH + ACK** | **데이터 전송** |
| `[F.]` | **FIN + ACK** | 연결 종료 요청 |
| `[R]` | **RST** | 연결 강제 거부/끊김 |

**`.` 은 항상 ACK 를 뜻한다.** `[S.]` = SYN 과 ACK 가 같이 붙은 것 = ②번 패킷.

### 동시에 터미널 1 을 보면

```
[서버] accept() 반환! → 3-way handshake 완료, ESTABLISHED 상태
```

**`accept()` 가 반환됐다는 건 handshake 가 이미 끝났다는 뜻이다.**
즉 Java 코드가 돌기 전에 OS 가 ①②③을 알아서 주고받았다.

## Step 4. 데이터 주고받기

**터미널 3** 에 아무거나 치고 엔터.
```
hello
```

터미널 2:
```
IP 127.0.0.1.61105 > 127.0.0.1.9000: Flags [P.], ... length 6     ← 내가 보낸 "hello\n"
IP 127.0.0.1.9000 > 127.0.0.1.61105: Flags [.],  ack 7            ← "받았다"
IP 127.0.0.1.9000 > 127.0.0.1.61105: Flags [P.], ... length 12    ← "ECHO: hello\n"
IP 127.0.0.1.61105 > 127.0.0.1.9000: Flags [.],  ack 13           ← "받았다"
```

**데이터를 보낼 때마다 상대가 ACK 를 돌려준다.** 이게 TCP 가 "신뢰성 있다"고 하는 이유다.
ACK 가 안 오면 **재전송**한다.

**터미널 3 에서 `netstat -an | grep 9000` 을 다시 해보면**
```
tcp4   0   0  127.0.0.1.9000    127.0.0.1.61105   ESTABLISHED
tcp4   0   0  127.0.0.1.61105   127.0.0.1.9000    ESTABLISHED
tcp4   0   0  *.9000            *.*               LISTEN
```
**세 줄이다.** 연결 하나는 **양쪽 끝이 각각 한 줄**씩, 그리고 `LISTEN` 은 계속 남아 다음 손님을 기다린다.

## Step 5. 종료 — 4-way 와 TIME_WAIT

**터미널 3** 에서 `bye` 를 치거나 `Ctrl + C`.

터미널 2:
```
IP ... Flags [F.]    ← ① FIN
IP ... Flags [.]     ← ② ACK
IP ... Flags [F.]    ← ③ FIN
IP ... Flags [.]     ← ④ ACK
```

**바로** 터미널 3 에서:
```bash
netstat -an | grep 9000
```
```
tcp4   0   0  127.0.0.1.61105   127.0.0.1.9000   TIME_WAIT
                                                 └─ 아직 안 사라졌다
```

**잠시 뒤 다시 확인하면 사라져 있다.** 이게 `TIME_WAIT` 이다.

# 면접 포인트

1. **3-way handshake 를 설명해보세요**
   → SYN / SYN+ACK / ACK. **양방향 통신이 모두 가능함을 서로 확인**하는 과정.
   2번이면 서버가 자기 패킷의 도착을 확인할 수 없다.

2. **연결은 3번인데 종료는 왜 4번인가요?**
   → TCP 는 **양방향**이라 각 방향을 따로 닫는다. 내가 끊어도 **상대는 보낼 게 남았을 수 있어서**
   ACK 와 FIN 을 합칠 수 없다.

3. **`TIME_WAIT` 은 왜 있나요?**
   → ① **마지막 ACK 가 유실됐을 때** 상대의 FIN 재전송을 받아주기 위해
   ② 이전 연결의 **늦은 패킷이 새 연결에 섞이는 것**을 막기 위해.
   트래픽이 많으면 포트 고갈의 원인이 되기도 한다.

4. **포트는 왜 필요한가요?**
   → IP 는 "어느 컴퓨터"까지만 알려준다. 한 컴퓨터의 **여러 프로그램 중 어디로 전달할지**
   구분하는 번호가 포트다.

5. **연결 하나를 식별하는 값은?**
   → **(출발 IP, 출발 포트, 도착 IP, 도착 포트)** 네 개. 그래서 같은 서버 포트에
   여러 클라이언트가 붙어도 섞이지 않는다.

## Q. 패킷이 데이터인가?

**패킷 = 데이터를 헤더로 감싼 한 덩어리.** 데이터 그 자체가 아니다.

```
"hello" 를 보낼 때 실제로 나가는 것
┌─────────────────┬──────────────────┬───────────┐
│    IP 헤더       │    TCP 헤더       │   데이터   │
│    20 bytes     │    20 bytes      │  6 bytes  │
├─────────────────┼──────────────────┼───────────┤
│ 출발 127.0.0.1  │ 출발포트 61105    │ h e l l o │
│ 도착 127.0.0.1  │ 도착포트 9000     │ \n        │
│ 프로토콜  TCP    │ 순서번호 12345    │           │
└─────────────────┴──────────────────┴───────────┘
  └──── 헤더 = 택배 송장 ────┘        └ 내용물 ┘
```

**SYN 패킷은 데이터가 0바이트다.** 빈 상자에 송장만 붙여 보내는 것 —
**송장에 적힌 글씨(`[S]` 플래그) 자체가 메시지**다.

### 왜 쪼개서 보내나
네트워크 장비가 한 번에 처리하는 크기(**MTU**, 보통 1500바이트)가 정해져 있다.
10MB 파일은 7000조각쯤으로 쪼개 보내고, 받는 쪽이 **seq 번호 순서대로 재조립**한다.
→ **이게 순서번호가 존재하는 이유다.**

실제 바이트를 보려면: `sudo tcpdump -i lo0 -n -X 'tcp port 9000'`

## Q. ServerSocket 과 Socket 의 차이는?

```
 ServerSocket  =  식당 입구의 안내 데스크      Socket  =  테이블
                  "어서오세요" 만 한다                   실제 주문과 식사
                  음식은 안 준다                         손님마다 하나씩
```

| | `ServerSocket` | `Socket` |
|---|---|---|
| 역할 | **연결을 받는다** | **데이터를 주고받는다** |
| 개수 | 포트당 1개 | **접속 수만큼** |
| 데이터 송수신 | ❌ 메서드 자체가 없다 | ✅ `getInputStream()` / `getOutputStream()` |
| 누가 만드나 | 내가 `new` | **`accept()` 가 만들어 반환** |
| 상태 | `LISTEN` | `ESTABLISHED` |

```
 ServerSocket (포트 9000, LISTEN)  ← 계속 남아 다음 손님을 기다린다
       │ accept()
       ├──▶ Socket #1   클라 61105 전용
       ├──▶ Socket #2   클라 61106 전용
       └──▶ Socket #3   클라 61107 전용
```

> OS 레벨에선 둘 다 소켓이다. **listening socket** / **connected socket** 으로 구분되는 것을
> Java 가 두 클래스로 나눠놓았다. `ServerSocket` 에 `getInputStream()` 이 **아예 없는 것**은
> "하면 안 되는 일을 애초에 못 하게" 만든 설계다. (Entity 에 setter 를 안 만든 것과 같은 발상)

## Q. 상태(LISTEN 등)는 누가 바꾸나?

**OS(커널)다. 내 코드가 아니다.**

```
  내 Java 코드                       OS (커널)
  new ServerSocket(9000)               │
       │ ──── "9000 쓸게" ────▶        │  포트 등록, 상태 = LISTEN  ✏️
  accept()                             │
       │ ──── "오면 깨워줘" ───▶        │  SYN 수신 → SYN-ACK 전송
       │      (여기서 멈춤)             │  ACK 수신 → ESTABLISHED  ✏️
       │ ◀──── Socket 반환 ────        │
```

**3-way handshake 는 전부 OS 가 한다.** 내 코드는 끝난 뒤 깨어난다.
`netstat` 이 보여주는 것도 OS 가 들고 있는 표다.

## Q. Gradle 이 왜 필요 없나?

`java.net.ServerSocket`, `java.net.Socket`, `java.io.*` 는 **전부 JDK 기본 포함**이다.
외부 라이브러리가 하나도 없으니 의존성 관리가 필요 없다.
**Java 11+ 는 `.java` 파일을 바로 실행**한다 → `java TcpEchoServer.java`

## Q. REST API 도 3-way handshake 를 하나?

**한다.** HTTP 는 TCP 위에 얹혀 있다.

```
 ┌──────────────────────────────┐
 │  내 코드   REST API 호출       │
 ├──────────────────────────────┤
 │  HTTP      "GET /posts"      │  ← 요청/응답 형식
 ├──────────────────────────────┤
 │  TCP       연결·순서·재전송    │  ← 3-way handshake 가 여기
 ├──────────────────────────────┤
 │  IP        주소 찾아가기       │
 ├──────────────────────────────┤
 │  이더넷/WiFi  실제 전기신호    │
 └──────────────────────────────┘
```

**단, 요청마다 하는 건 아니다.**

```
 HTTP/1.0        handshake → 요청 → 응답 → 종료   (매번) 💥
 HTTP/1.1+       handshake → 요청/응답 × N → 종료  ← keep-alive
```

**통로를 먼저 뚫고, 그 위로 계속 주고받는다.**
실습에서 `nc` 로 여러 줄을 쳐도 **`[S]` 는 맨 처음 한 번만** 나오는 것이 증거다.

### 로딩 시간의 정체
```
 ① DNS 조회       ~20ms   "그 도메인의 IP 가 뭐야?"
 ② TCP handshake  ~30ms
 ③ TLS handshake  ~60ms   (HTTPS면) — 더 비싸다
 ④ HTTP 요청/응답  ~50ms   실제 데이터
```
handshake 는 **일부**일 뿐. 보통 서버 처리 시간과 TLS 가 더 크다.

> **HikariCP(DB 커넥션 풀)와 같은 발상이다.** 연결 수립이 비싸니 미리 만들어두고 재사용한다.

## Q. 연결이 중간에 끊기면? 예외 처리를 해야 하나?

### 상황 ① 서버가 안 떠 있다 → **즉시 거부**
```
  클라 ── ① SYN ──────────▶  (포트에 LISTEN 중인 게 없음)
  클라 ◀─ ② RST ──────────   "그런 포트 안 열려있어"
  ❌ java.net.ConnectException: Connection refused    (즉시)
```

### 상황 ② 응답이 없다 → **타임아웃** ⚠️ 더 위험
```
  클라 ── SYN ──X          1초 대기
  클라 ── SYN ──X          2초 대기
  클라 ── SYN ──X          4초... 8초... 16초...  (간격이 2배씩)
  ❌ SocketTimeoutException  또는 설정 안 했으면 무한정 대기
```

### 상황 ③ 연결 중 끊김
```
  ═══ ESTABLISHED ═══  →  서버 프로세스 강제 종료 → RST
  ❌ java.net.SocketException: Connection reset
```

### 내가 예외 처리를 해야 하나?

| 하는 일 | 책임 |
|---|---|
| **Spring Boot 서버 개발** | **거의 없음.** 톰캣이 처리한다 |
| **외부 API 호출** | ⚠️ **타임아웃 설정이 필수** |
| **소켓 직접** | 전부 직접 (`IOException`) |

```java
// ❌ 상대가 응답 안 하면 영원히 멈춘다
RestTemplate restTemplate = new RestTemplate();

// ✅
RestTemplate restTemplate = new RestTemplateBuilder()
        .connectTimeout(Duration.ofSeconds(3))
        .readTimeout(Duration.ofSeconds(5))
        .build();
```

**타임아웃이 없으면 장애가 전파된다.**
```
 외부 API 느려짐 → 내 요청 처리 스레드가 거기 묶임
   → 요청이 쌓이며 스레드가 하나씩 더 묶임
     → 톰캣 스레드 200개 소진 → 💀 내 서버 전체가 멈춤
```
**cascading failure.** "외부 API 연동 시 주의할 점"의 1번 답이다.

## Q. IPv4 와 IPv6, 그리고 `tcp46` 은?

```
 IPv4   32비트   127.0.0.1   약 43억 개   (1981년. 이미 고갈)
 IPv6  128비트   ::1         사실상 무한
```
`::1` 은 `0000:...:0001` 의 줄임. **연속된 0을 `::` 로 압축**한다.

```
tcp46   *.9000   *.*   LISTEN
  ▲
  └─ IPv4 와 IPv6 둘 다 받는다 (dual-stack). Java ServerSocket 의 기본 동작
```

**macOS 는 `localhost` 를 IPv6(`::1`)로 먼저 시도**한다.
→ 출력이 `[0:0:0:0:0:0:0:1]` 처럼 길어져 읽기 불편하다.
→ 실습에선 **`127.0.0.1`** 을 써서 IPv4 로 강제한다.

## Q. `netstat` 출력을 어떻게 읽나?

```
Proto  Recv-Q Send-Q  Local Address      Foreign Address    (state)
tcp46    0      0     *.9000             *.*                LISTEN
tcp4     0      0     127.0.0.1.62216    127.0.0.1.9000     TIME_WAIT
  ①      ②      ③       ④                  ⑤                  ⑥
```

| | 컬럼 | 뜻 |
|---|---|---|
| ① | `Proto` | `tcp4`=IPv4 / `tcp46`=둘 다 |
| ② | `Recv-Q` | **받았는데 앱이 아직 안 읽은** 바이트. 쌓이면 앱이 느린 것 |
| ③ | `Send-Q` | **보냈는데 ACK 못 받은** 바이트. 쌓이면 네트워크 문제 |
| ④ | `Local Address` | **이 줄의 주인** |
| ⑤ | `Foreign Address` | 그 상대 |
| ⑥ | `(state)` | 연결 상태 |

- `*.9000` = 어느 IP 로 들어오든 9000 포트면 받겠다 (와일드카드)
- `*.*` = 아직 상대가 없다

### ⭐ 누가 먼저 끊었는지 판별하는 법

**`TIME_WAIT` 이 붙은 줄의 `Local` 포트를 본다.**

| `Local` 포트 | 그 줄의 정체 | 결론 |
|---|---|---|
| **9000** (서버 포트) | 서버 쪽 소켓 | **서버가 먼저 끊었다** |
| **62216** (임의의 큰 수) | 클라 쪽 소켓 | **클라이언트가 먼저 끊었다** |

실제로 확인한 것:
```
 bye 입력     → tcp4  127.0.0.1.9000    127.0.0.1.61731  TIME_WAIT   서버가 끊음
 Ctrl+C       → tcp4  127.0.0.1.62216   127.0.0.1.9000   TIME_WAIT   클라가 끊음
```
**localhost 통신이라 양쪽이 모두 내 컴퓨터에 있어서 둘 다 보인다.**
실제 서비스라면 각자의 `netstat` 에 자기 쪽 한 줄만 나온다.

## Q. ACK 가 왜 데이터 보낼 때도 같이 가나? ⭐

**ACK 는 "답장"이 아니라 "내 수신 상태 보고"다.**

```
 ┌─────────────────────────────┐
 │  안녕, 잘 지내?               │  ← 본문 (데이터)
 │  ps. 난 네 편지 3번까지 받았어 │  ← ACK
 └─────────────────────────────┘
```
`ps.` 줄은 본문 내용과 아무 상관이 없다. **그냥 어디까지 받았는지 알리는 것**이다.

### 왜 매번 붙이나 — **공짜라서**
```
 TCP 헤더 (20 bytes 고정)
 ┌──────────────────┬──────────────────┐
 │   출발 포트       │   도착 포트       │
 ├──────────────────┴──────────────────┤
 │        순서번호 (seq)  4 bytes       │  내가 보내는 위치
 ├─────────────────────────────────────┤
 │        확인번호 (ack)  4 bytes       │  내가 받은 위치 ← 자리가 항상 있다
 └─────────────────────────────────────┘
```
ACK 를 안 켜도 그 4바이트는 어차피 들어간다. **켜면 정보 하나를 공짜로 더 전달**한다.
→ 안 켤 이유가 없다.

### 💡 `[S]` 만 점이 없는 이유
```
 [S]    ← ACK 없음   ⚠️ 유일
 [S.] [.] [P.] [F.]  ← 전부 ACK 있음
```
**첫 SYN 시점엔 상대한테서 받은 게 아무것도 없어서 보고할 게 없다.**
→ 이 관찰 하나가 "ACK = 수신 상태 보고" 를 증명한다.

### 실제 출력 해독
```
IP 127.0.0.1.62216 > 127.0.0.1.9000: Flags [P.], seq 1:7, ack 1, win 6380, length 6
                                            │       │       │      │          │
                                          PSH+ACK  1~6번  1번부터  수신버퍼   데이터
                                                   보낸다  기다림   여유      6바이트

IP 127.0.0.1.9000 > 127.0.0.1.62216: Flags [.], ack 7, length 0
                                                  │        │
                                            "1~6 받았으니  데이터 없음
                                             다음은 7부터"  = 순수 ACK
```
**ACK 번호 = 받은 마지막 번호 + 1 = "다음에 기대하는 번호"**
→ 중간에 하나가 빠지면 ACK 번호가 안 올라가서 **바로 티가 난다.**

## Q. ACK 가 없으면 어떻게 되나?

```
 [ACK 가 없다면]
   클라 ──"hello"──X        (유실)
   클라: "보냈으니 됐지"      → 서버는 영영 못 받음
   💥 아무도 모른 채 데이터가 사라진다

 [ACK 가 있으면]
   클라 ──"hello"──X        (유실)
   클라: "...ACK 가 안 오네?"
   클라 ──"hello"────────▶  🔁 재전송 → 도착
```
**ACK 는 영수증.** 안 오면 다시 보낸다. **이게 TCP 가 "신뢰성 있다"는 말의 전부다.**
그리고 **그래서 느리다.**

## Q. 왜 서버는 ACK 만 주면 되는데 SYN 까지 같이 보내나? ⭐

**논리적으로는 4단계인데, 두 개를 합쳐서 3번이 된 것이다.**

```
 ┌─ 논리적으로 4단계 ────────────────────────────┐
 │  ① SYN   클라 ──▶ 서버   "클라→서버 방향 열자"  │
 │  ② ACK   클라 ◀── 서버   "좋아"                │
 │  ③ SYN   클라 ◀── 서버   "서버→클라도 열자"     │
 │  ④ ACK   클라 ──▶ 서버   "좋아"                │
 └───────────────────────────────────────────────┘
          ② 와 ③ 은 둘 다 서버가 보낸다 → 한 패킷에 합친다
                            ▼
 ┌─ 실제 3단계 ──────────────────────────────────┐
 │  ① [S]   SYN                                 │
 │  ② [S.]  SYN + ACK   ← 합쳐짐                 │
 │  ③ [.]   ACK                                 │
 └───────────────────────────────────────────────┘
```

**연결은 양방향이라 각 방향을 따로 열어야 한다.**

### 💡 그래서 종료가 4번인 이유도 같이 풀린다
```
 연결:  ②③ 을 합칠 수 있다 → 3번   (서버가 바로 "나도 열자" 할 수 있으니까)
 종료:  ②③ 을 합칠 수 없다 → 4번   (내가 끊어도 서버는 보낼 게 남았을 수 있으니까)
```
**둘 다 "양방향이라 각 방향을 따로 처리한다"는 같은 원리다.**

## Q. SYN 에 데이터가 뭐가 들어있나?

**데이터는 0바이트. 하지만 헤더에 핵심 정보가 있다.**

**SYN = Synchronize(동기화).** 뭘 동기화하나? → **순서번호를.**

```
 ① [S]   seq 1234567890
         "내 데이터는 1234567890번부터 시작할게"
 ② [S.]  seq 987654321, ack 1234567891
         "내 건 987654321번부터"  (SYN)
         "네 거 받았으니 다음은 ...891"  (ACK)
 ③ [.]   ack 987654322
         "네 거 받았으니 다음은 ...322"
```

**양쪽이 서로의 시작 번호를 알려주고 확인하는 과정이다.**
쪼개서 보낸 조각을 순서대로 재조립하려면 시작 번호를 알아야 한다.
→ **데이터를 보내기 전에 미리 맞춰두는 것.**

| 헤더 필드 | 뜻 |
|---|---|
| `seq` | **내 순서번호 시작값** ← 가장 중요 |
| `win` | "한 번에 이만큼까지 받을 수 있어" (흐름 제어) |
| `mss` | "한 패킷은 이 크기를 넘기지 마" |

**연결을 열면서 통신 규칙을 맞추는 것** — 그래서 **handshake(악수)** 다.

# 5부. 복습 방법

> **직접 보고 만든 건 남고, 읽기만 한 건 안 남는다.**
> 복습도 "다시 읽기"가 아니라 **"다시 해보기"** 여야 한다.

| 시점 | 방법 | 시간 |
|---|---|---|
| **오늘** | 3부 체크리스트 8개를 **소리 내어** 답하기 | 10분 |
| **내일** | **백지 테스트** — 아무것도 안 보고 3-way/4-way 화살표와 상태 이름 그리기 → 문서와 대조 | 5분 |
| **3일 뒤** | **실습 재현** — 명령어를 안 보고 터미널 3개 다시 띄우기 | 10분 |
| **다음 실습** | **UDP 실습이 곧 TCP 복습이다.** "TCP는 어땠더라?" 를 계속 떠올리게 된다 | — |

**백지 테스트가 효율이 가장 높다.** 읽을 땐 다 아는 것 같은데 그려보면 꼭 하나씩 빠진다.

## 2026-10-21 (3일차) — 🟢 유지

**Q1. TCP 와 UDP 의 차이는?**

> TCP는 핸드쉐이크를 통해 연결 및 끊기를 진행합니다. UDP는 핸드쉐이크를 사용하지 않아도
> 연결이 가능하다. TCP같은 경우는 중요한 데이터 즉 빠짐없이 데이터를 받아야 하는 경우
> 사용한다. 헤더안에 순서를 표시하는 게 있기 때문에 어디까지 데이터를 받고 있는지 확인할 수
> 있다. 반대로 UDP는 중요한 데이터보다 끊기지 않고 지속적으로 연결이 되도록 하는 것을
> MAIN으로 두고 있기 때문에 데이터가 빠져도 큰 문제 없는 통신에서 자주 사용한다.

**Q2. UDP 를 쓰는 게 나은 경우는?**

> 방송, 게임 같은 것이다. 이것들은 중간중간 끊기면 사용자에게 불편함을 줘서 UDP를 사용한다.
> TCP를 사용하게 되면 버퍼링이 생길 수 있기 때문이다.

**꼬리. 보내는 쪽은 상대가 받았는지 어떻게 아나? 못 받았으면?**

> 보낼 때 ACK를 같이 보냅니다. 거기에 순서 정보가 있습니다.
> 못 받았으면 다시 재요청 하게 되고 지속적으로 문제가 생기면 끊기는 걸로 알고 있습니다

### 채점 — 🟢

```
 ✅  handshake 유무
 ✅  순서번호로 어디까지 받았는지
 ✅  빠짐없이 vs 빠져도 되는
 ✅  방송·게임.  "TCP 면 버퍼링"  ← head-of-line blocking 을 현상으로 정확히 짚음
```

**블로그를 쓴 효과가 보인다.** 10/10 체크리스트에선 🟡·🔴 가 섞였는데 이번엔 말로 나왔다.

### 보완 — 방향이 두 군데 뒤집혔다

```
 ❌  보낼 때 ACK 를 같이 보냅니다
 ✅  ACK 는 받은 쪽이 보낸다.  보낸 쪽은 ACK 를 받는다
```

```
 클라 → 서버    [P.] "hello"        데이터
 서버 → 클라    [.]  ack 7          받았다       ← 받은 쪽이 보낸다
```

`[P.]` 처럼 데이터와 ACK 가 한 패킷에 실리는 건 맞다. 양방향이라 묶어 보낸다.
다만 **ACK 자체의 주체는 받은 쪽**이다.

```
 ❌  못 받았으면 다시 재요청한다
 ✅  보낸 쪽이 ACK 를 못 받으면 타이머 만료 후 재전송한다
```

```
 받는 쪽은 뭐가 안 왔는지 모를 수도 있다      아예 유실됐으면 흔적이 없다
 보낸 쪽이  ACK 를 기다린다 → 안 온다 → 재전송
```

**"재요청" 이 아니라 "재전송".** 주체가 반대다.

### 용어 하나 붙이면 좋다

```
 "TCP 면 버퍼링이 생긴다"   →   head-of-line blocking
```

③이 유실되면 ④⑤가 도착해 있어도 앱에 못 올라간다. 순서를 보장하려다 뒤가 다 밀린다.
현상은 정확히 설명했으니 **이름만 붙이면 된다.**
