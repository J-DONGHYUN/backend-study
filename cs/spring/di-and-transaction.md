**Q1. 의존성 주입 중 생성자 주입을 쓰는 이유는?**

> 생성자 주입을 해야 해당 클래스에서 어떤 의존성을 받고 있는지 확인할 수 있다.

**Q2. 당신은 어떻게 적용했나요?**

> 저는 스프링 프레임워크를 사용하여 개발을 진행했습니다. 이러한 이유로 생성자 주입을 할 때
> 의존성이 있는 건 NEW를 안해도 빈으로 등록이되어 그것을 생성자를 통해 주입했습니다.

**꼬리. 필드 주입이었다면 단위 테스트에서 가짜 Repository 를 어떻게 넣나요?**

> 주입할 수 없다.


**Q1. `@Transactional(readOnly = true)` 를 붙이면 무슨 일이 일어나나요?**

> 트랜잭션을 진행하면 더티체킹 등 하이버네이트가 하는일들이 많지만 readOnly는 조회용이기
> 때문에 그런 행위가 필요없어서 진행을 하지않는다.

**Q2. 어디에 붙였나요?**

> GET 메서드에 붙임. 말 그대로 조회용이니까 → (확인) Service 의 조회 메서드

**꼬리. 조회 메서드가 10개면 10개에 전부 붙이나요?**

> 붙여야지

#### 채점 — 🟢 유지

Q1 정확. 스냅샷을 안 만들고 더티체킹 대상에서 빠진다. 선언 위치(Service)도 정확.

**보완 — 클래스 레벨 기본값**

```java
@Service
@Transactional(readOnly = true)          // 클래스 기본값
public class PostService {
    public PostResponse findById(...) { }        // 그냥 쓰면 readOnly
    public Page<...> findAll(...) { }

    @Transactional                               // 쓰기만 덮어쓴다
    public PostResponse create(...) { }
}
```

```
 ▸ 중복이 사라진다
 ▸ 안전한 기본값      새 조회 메서드를 추가하면서 깜빡해도 readOnly 가 걸린다  ★
 ▸ 쓰기가 눈에 띈다    @Transactional 이 붙은 메서드 = 데이터를 바꾸는 메서드
```

두 번째가 핵심. **안 붙이는 실수보다 잘못 붙는 실수가 덜 위험한 쪽**을 기본값으로 둔 것.
