# Interview Log — Todo CRUD API (과제 #1)

> 이 과제의 면접 대비 기록. 모의 면접 답변과 보완 내용.
> 과제 개요/설계/회고는 같은 폴더의 `README.md` 참고.

## 무엇을 만들었나
Spring Boot + JPA + H2로 Todo 관리 REST API. 등록/단건조회/목록조회(필터)/수정/완료처리/삭제 6개 엔드포인트.
계층은 Controller / Service / Repository / Domain으로 분리. 테스트 19개(단위·통합·E2E).

## 최종 API 설계
| 기능 | Method | Path | 성공 status |
|---|---|---|---|
| 등록 | POST | `/todos` | 201 |
| 단건 조회 | GET | `/todos/{id}` | 200 |
| 목록 조회 | GET | `/todos?completed=` | 200 |
| 수정 | PUT | `/todos/{id}` | 200 |
| 완료 처리 | PATCH | `/todos/{id}/complete` | 200 |
| 삭제 | DELETE | `/todos/{id}` | 204 |

에러: 404(없는 id) / 409(중복 완료) / 400(검증 실패). 전부 `{status, message, timestamp}` 형식.

## 주요 설계 결정과 이유
- **완료 처리를 별도 엔드포인트로 분리** — 일반 수정과 **적용되는 규칙이 다르기 때문**(이미 완료면 거부). 합치면 요청마다 "이번이 완료 요청인가"를 따져야 한다.
- **요청 DTO를 등록/수정으로 분리** — 지금은 내용이 같지만, 요구 필드와 검증 규칙이 갈라질 때 변경 비용이 낮다.
- **"이미 완료면 거부" 규칙을 Entity 안에** — 어디서 호출하든 규칙이 따라온다. Service에 두면 다른 Service·배치가 검사를 빠뜨릴 수 있다.
- **Entity에 setter 없음** — 대신 `complete()`, `update()` 같은 **동작 이름을 가진 메서드**. setter가 있으면 규칙을 우회할 수 있다.
- **`@Size`는 DTO, `@Column`은 Entity** — 사용자 입력 검증과 DB 제약은 역할이 다르다. DB 제약은 애플리케이션을 우회하는 경로에 대한 최후 방어선.
- **`BaseEntity` + `@MappedSuperclass`** — 시각 필드 중복 제거. 테이블은 생기지 않고 컬럼만 상속된다.

## 모의 면접 10문항 (2026-10-07)

### 🟢 Q5. 수정할 때 `save()`를 안 불렀는데 어떻게 DB에 반영되나?
**내 답변 (정확):** 1차 캐시와 스냅샷에 데이터가 있다. update 메서드를 실행하면 1차 캐시는 바뀌고 스냅샷은 그대로다. 여기서 더티 체크가 들어가고, 커밋할 때 1차 캐시 내용이 DB에 저장된다.
**보완:** 커밋 직전에 **flush**가 일어나고 그때 UPDATE 쿼리가 나간다.

### 🟢 Q4. "이미 완료면 거부" 규칙을 왜 Entity에 뒀나?
**내 답변 (정확):** Service는 실행 로직을 위한 것이고, 도메인 규칙은 도메인에서 잡아야 한다.
**보완:** "규칙이 엔티티 안에 있으면 **어디서 호출하든 규칙이 따라온다**"를 덧붙이면 설득력이 올라간다.

### 🟢 Q7. `@MappedSuperclass`를 쓴 이유? `@Entity`와 차이는?
**내 답변 (정확):** `@Entity`로 선언하면 독립 테이블이 생긴다. `@MappedSuperclass`는 상속시켜서 컬럼만 넣는다.
**보완:** `@MappedSuperclass`는 **조회 대상이 아니다.** `em.find(BaseEntity.class, ...)` 불가.

### 🔴 Q2. Entity를 API 응답으로 직접 반환하면 안 되는 이유?
**내 답변 (틀림):** Entity 코드에 필드 이외의 것들이 많아서. → Jackson은 getter만 보므로 메서드가 많은 건 상관없다.
**정답 (4가지, 면접에선 1·2만 말해도 충분):**
1. **API 스펙과 DB 스키마가 묶인다.** 컬럼을 추가하면 API 응답이 클라이언트 모르게 바뀐다. 둘은 따로 변해야 한다.
2. **민감 정보 노출.** User 엔티티면 password가 그대로 JSON에 실린다.
3. **지연 로딩 문제.** 직렬화 중 `LazyInitializationException` 또는 N+1 쿼리 폭발.
4. **양방향 연관관계면 무한 순환 참조** → StackOverflowError.

### 🔴 Q6. `@Transactional(readOnly = true)`를 왜 쓰나?
**내 답변 (틀림):** CPU 점유 비용. 롤백이 필요 없으니까. → 롤백과 무관하고 너무 막연하다.
**정답:** **Q5에서 말한 그 스냅샷을 만들지 않는다.** 조회한 엔티티마다 복사본을 들고 커밋 때 비교하는데, 읽기 전용이면 그 복사와 비교를 통째로 건너뛴다. 1000건 조회하면 스냅샷 1000개가 안 생긴다.
부가: flush 모드가 MANUAL이 되어 불필요한 flush 방지, 읽기 전용 replica 라우팅 가능, 의도 표현.
**교훈: Q5와 Q6은 같은 메커니즘의 앞뒷면인데 따로 외워서 연결이 안 됐다.**

### 🔴 Q8. 생성자 주입을 쓴 이유? (필드 주입과 비교)
**내 답변:** 모름.
**정답:**
| | 생성자 주입 | 필드 주입 |
|---|---|---|
| `final` | 가능 → 생성 후 교체 불가 | 불가능 |
| 테스트 | `new TodoService(mock)` 가능 | 컨테이너 필요 |
| 객체 상태 | 항상 완전함 | 주입 전까지 `null` 구간 존재 |
| 순환 참조 | 앱 시작 시 발견 | 운영 중 발견 |

**면접 답변은 "테스트하기 쉽고, 의존성이 빠진 불완전한 객체가 만들어지지 않는다" 두 가지.**
**이미 경험함:** `@InjectMocks`가 동작한 게 생성자 주입 덕분이다.

### 🔴 Q3. 완료 처리를 왜 별도 엔드포인트로?
**내 답변:** 의도를 보여줘야 한다고 생각했다. (PUT/PATCH 얘기와 섞여 답이 흐려짐)
**정답:** **완료는 일반 수정과 규칙이 다르다.** 이미 완료면 거부해야 하는데, 같은 엔드포인트면 "이번 요청이 완료 요청인지"를 매번 따져야 한다.

### 🟡 Q1. 계층을 왜 나누나?
**내 답변:** 지저분하지 않고, 캡슐화를 지키고, 다른 개발자가 보기 쉽다. (외부 DB 영역을 나누는 이유는 모르겠다)
**보완 — "읽기 쉽다"는 주관이라 약하다. 세 가지로:**
1. **변경의 격리.** DB 기술을 바꿔도 Service의 비즈니스 로직은 한 줄도 안 바뀐다.
2. **바뀌는 이유가 다르다.** Controller=API 스펙, Service=업무 규칙, Repository=저장 기술.
3. **테스트.** Repository를 가짜로 갈아끼워 Service만 검증할 수 있었던 건 계층이 나뉘어 있어서다.

### 🟡 Q9. Controller에 try-catch가 없는데 어떻게 404가 나가나?
**내 답변:** unchecked 예외는 try-catch가 필요 없고, 공통 예외 핸들러에서 매핑 후 응답한다.
**보완 — "그럼 누가 잡나"가 빠졌다.** **`DispatcherServlet`이 이미 try-catch로 감싸고 있다.** 예외가 나면 `HandlerExceptionResolver` 체인으로 넘어가고, `@RestControllerAdvice`는 **거기에 "이 예외는 이렇게 처리해라"는 규칙을 등록**하는 것이다. 새 try-catch를 만드는 게 아니다.

### 🟡 Q10. 단위/통합/E2E는 각각 뭘 검증하나? 왜 셋 다 필요한가?
**내 답변:** 단위=단순 로직, 통합=실제 DB 연결, E2E=API를 직접 쏴서 처음부터 끝까지.
**보완 — "왜 셋 다"가 빠졌다. 속도와 신뢰도의 트레이드오프.** 단위는 빠르고 원인이 명확하지만 "진짜 되는지"는 모르고, E2E는 확실하지만 느리고 깨졌을 때 범인을 못 찾는다. 그래서 피라미드로 쌓는다(단위 많이 → E2E 적게).

## 추가로 알게 된 것

### 멱등(idempotent)
같은 요청을 몇 번 보내도 결과가 같은 성질. **네트워크가 끊겨 응답을 못 받았을 때 그냥 재시도해도 안전**하다는 게 핵심 가치.
- 멱등: GET, PUT, DELETE / 멱등 아님: POST / PATCH는 구현하기 나름
- **우리 `PATCH /todos/{id}/complete`는 멱등이 아니다** (2번째 호출은 409). 요구사항상 맞는 설계지만 "멱등하게 만들 수도 있지 않나요?"는 나올 수 있는 질문.

### 테스트 격리 (실제로 겪은 버그)
E2E 테스트는 **실제 HTTP라 서버 스레드가 처리**하므로 테스트 스레드의 `@Transactional` 롤백이 통하지 않는다. 커밋된 데이터가 같은 H2(`jdbc:h2:mem:tododb`)를 쓰는 통합 테스트를 오염시켜, `hasSize(3)` 단언이 깨졌다.
**더 무서운 건 처음엔 통과했다가 실행 순서가 바뀌며 터진 것(flaky test).** 항상 실패하는 테스트보다 나쁘다 — 사람들이 테스트 전체를 안 믿게 된다.
**해결:** E2E에 `@AfterEach { todoRepository.deleteAll(); }`.

### `save()`가 반환하는 것
**"영속 상태가 된 엔티티".** 확인용이 아니다.
- 새 엔티티 → `persist` → **내가 넘긴 그 객체**가 영속화되어 그대로 반환
- 준영속 엔티티 → `merge` → **다른 객체**에 값만 복사해 반환. 원본은 여전히 준영속이라 **바꿔도 DB에 반영 안 됨**
→ 어느 쪽인지 매번 따지지 말고 **항상 반환값을 쓰는 습관**.

## 오늘의 메타 교훈
**직접 만들고 눈으로 확인한 것(변경 감지, `@MappedSuperclass`)은 정확히 설명했고, 말로만 들은 것(생성자 주입, readOnly, Entity 직접 반환)은 흐릿했다.**
→ 다음 과제부터는 설명을 들은 개념도 **반드시 코드나 로그로 확인하는 단계**를 넣을 것.
