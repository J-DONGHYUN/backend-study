# 과제 #3 — 선착순 쿠폰 발급 API

> 상태: **설계 진행 중** (엔티티 확정 / API 설계 중단)

## 요구사항

```
 1  쿠폰 이벤트 생성       이름, 총 발급 수량
 2  쿠폰 발급 요청         회원이 신청한다
 3  남은 수량 조회
```

**제약 — 이걸 지키는 게 과제의 전부다.**

```
 ①  총 수량을 1장이라도 초과하면 안 된다
 ②  같은 회원이 두 번 받을 수 없다
 ③  수량이 소진되면 적절한 에러를 반환한다
```

## 진행 방식 — 지금까지와 다르다

```
 STEP 1   기능을 평범하게 완성한다            ← 동시성 신경 쓰지 말고
 STEP 2   동시성 테스트를 짜서 터뜨린다        ★ 이게 핵심
 STEP 3   고친다
 STEP 4   측정하고 회고
```

```
 재고 100장  +  동시 신청 100명   →   몇 장이 나갈까?
```

**STEP 2에서 깨지는 걸 반드시 눈으로 봐야 한다.** 과제 #2에서 쿼리 12개를 직접 세어본 것과 같다.
그래서 STEP 1에서는 일부러 대책 없이 짠다. 미리 방어하면 STEP 2에서 볼 게 없어진다.

> 해결 방법은 STEP 3에서 꺼낸다. 터지는 걸 먼저 볼 것.

## 기술 제약

Java, Spring Boot, Gradle, H2(인메모리). H2도 비관적 락·격리 수준·`@Version`을 전부 지원한다.

## 내 설계

### 1. 엔티티 — 확정

처음엔 `Member`, `Coupon` 둘만 두고 연관관계도 없다고 봤다. 제약 ②(같은 회원 두 번 불가)를
어떻게 확인하느냐는 질문에서 연관이 필요하다는 걸 알았다.

그다음 막힌 건 **"100장 한정"을 어디에 적느냐**였다. `Coupon` 한 행이 "발급된 1장"이면
아직 아무도 안 받았을 때 행이 0개라 `100`을 적을 곳이 없다.

→ **`쿠폰`이라는 한 단어가 두 가지를 가리키고 있었다.**

```
 "여름 할인 쿠폰, 100장 한정"      기획자가 만드는 것    이벤트당 1개
 "김동현이 받은 1장"               사용자가 받는 것      사람 수만큼
```

SQL 연습에서 쓰던 스키마가 같은 구조였다.

```
 product      id, name, price, stock          ← 종류.  재고는 여기
 order_item   order_id, product_id, quantity  ← 실제 거래 1건
```

**최종**

```
 Member  1 ──< CouponIssue >── 1  Coupon
                   N
```

N:M 관계를 중간 엔티티로 푼 것. JPA에서 `@ManyToMany`를 쓰지 않고 중간 엔티티를 직접 만드는 게 정석.

| 엔티티 | 필드 |
|---|---|
| `Member` | `name` |
| `Coupon` | `name`, `totalQuantity`, `issuedCount` |
| `CouponIssue` | `member_id` (FK), `coupon_id` (FK), `issuedAt` |

**이름을 `MemberCoupon`이 아니라 `CouponIssue`로 한 이유**
이 테이블은 단순 연결이 아니라 자기 정보(발급 시각, 사용 여부)를 갖는다.
`order_item`에 `quantity`와 `unit_price`가 있던 것과 같다. 연결용 이름보다 **사건 이름**이 맞다.

**`category` 를 뺐다** — 요구사항에 없다. 당장 안 쓰는 필드를 "나중에 쓸 것 같아서" 넣는 건 YAGNI 위반.

**`issuedAt` 을 넣은 이유** — "선착순"이라는 단어 자체가 시간을 전제한다.
`BaseEntity`의 `createdAt`은 "이 행이 언제 생겼나"고 `issuedAt`은 "쿠폰이 언제 발급됐나"다.
지금은 같은 값이지만 뜻이 다르고, 나중에 "발급 후 7일 뒤 만료"가 붙으면 의미가 꼬인다.

### 2. 재고를 어떻게 표현하나 — A 선택

```
 A.  Coupon 에 숫자를 들고 있는다
     totalQuantity = 100,  issuedCount = 37        →  남은 건 63

 B.  Coupon 에는 총량만 두고, 발급 수는 셀 때마다 센다
     SELECT COUNT(*) FROM coupon_issue WHERE coupon_id = 1
```

```
         속도        정확성
 A       빠름        issuedCount 와 실제 행 수가 어긋날 수 있다
 B       느림        항상 정확하다. 셀 때마다 진짜를 세니까
```

**A를 골랐다.** 같은 사실을 두 군데 적어두는 **비정규화**다. 속도를 위해 일부러 중복을 허용한다.
선착순 쿠폰처럼 조회가 폭발하는 상황에선 A가 맞다.

> A를 고른 대가는 STEP 2에서 보게 된다.

**교정 받은 것:** B가 느린 건 맞지만 "풀스캔"은 틀렸다. `coupon_id`에 인덱스가 있으면
인덱스 레인지 스캔이다. 결론은 맞고 설명이 틀렸다.

### 3. API — ⏸ 진행 중

| 기능 | Method | Path | 요청 | status |
|---|---|---|---|---|
| 쿠폰 이벤트 생성 | POST | `/coupons` | `{name, totalQuantity}` | 201 |
| 쿠폰 발급 요청 | POST | `/coupons/{couponId}` ⚠️ | `{name}` ⚠️ | 200 ⚠️ |
| 남은 수량 조회 | GET | `/coupons/{couponId}` | - | 200 |

**중단 지점:** 발급 요청의 요청 바디 `{name}`이 누구 이름인지, 이름으로 회원을 찾으면
동명이인은 어떻게 되는지에서 멈춤.
