"TCP는 신뢰성이 있고 UDP는 없다." 외우긴 했는데 그게 무슨 뜻인지는 몰랐습니다.
손실이 난다는 게 실제로 어떤 건지 보고 싶어서 직접 돌려봤습니다.

---

## 둘을 나란히 놓으면

```
            TCP                                    UDP
    클라이언트        서버                   클라이언트        서버
        │             │                        │             │
        │ ── SYN ───▶ │                        │             │
        │ ◀─ SYN+ACK ─│   연결부터 맺는다        │             │   연결이 없다
        │ ── ACK ───▶ │                        │             │
        │             │                        │             │
        │ ── data ──▶ │                        │ ── data ──▶ │
        │ ◀─ ack ──── │   도착을 확인한다        │ ── data ──▶ │   확인하지 않는다
        │ ── data ──▶ │                        │ ── data ──▶ │
        │ ◀─ ack ──── │                        │ ─ data ─ ✗  │   사라져도 모른다
        │             │                        │             │
        │ ── FIN ───▶ │                        │             │
        │ ◀─ ACK ──── │   끝낼 때도 절차가       │             │   끝도 없다
        │ ◀─ FIN ──── │   있다                  │             │
        │ ── ACK ───▶ │                        │             │
```

TCP는 패킷 하나를 보내는 데 앞뒤로 할 일이 많습니다. UDP는 그냥 던집니다.

---

## 헤더를 보면 이유가 보인다

```
 TCP 헤더 (20 bytes)                    UDP 헤더 (8 bytes)
 ┌─────────────┬─────────────┐         ┌─────────────┬─────────────┐
 │  출발 포트    │  도착 포트    │         │  출발 포트     │  도착 포트    │
 ├─────────────┴─────────────┤         ├─────────────┼─────────────┤
 │      순서번호 (seq)         │         │    길이      │   체크섬      │
 ├───────────────────────────┤         └─────────────┴─────────────┘
 │      확인번호 (ack)         │
 ├──────┬────────────────────┤          seq 도 ack 도 없다
 │ 플래그 │   윈도우 크기        │          순서를 맞출 수도
 ├──────┴────────────────────┤          재전송을 할 수도 없다
 │   체크섬      │  긴급 포인터  │
 └─────────────┴─────────────┘          적을 칸 자체가 없다
```

UDP가 기능을 뺀 게 아니라 **처음부터 그런 칸을 만들지 않았습니다.** 순서를 맞추려면 순서번호를 적을 자리가 있어야 하고, 재전송하려면 뭘 못 받았는지 알려줄 자리가 있어야 하는데, 둘 다 없습니다.

헤더가 20바이트에서 8바이트로 줄어든 건 그 대가입니다.

## 코드에도 그대로 드러난다

```java
// ───── TCP ─────                     // ───── UDP ─────
ServerSocket server =                  DatagramSocket socket =
    new ServerSocket(9000);                new DatagramSocket(9001);
Socket client = server.accept();       // accept() 가 없다

client.getInputStream().read(...);     DatagramPacket p = new DatagramPacket(buf, len);
                                       socket.receive(p);

// 상대는 소켓이 기억한다                p.getAddress();  p.getPort();
                                       // 상대 주소를 패킷에서 꺼내야 한다
```

```
                 TCP                         UDP
 ──────────────────────────────────────────────────────────
 클래스          ServerSocket + Socket       DatagramSocket 하나
 연결 대기        accept()                   없음 — 바로 receive()
 상대 주소        소켓이 기억한다               패킷에서 꺼낸다
```

처음엔 "UDP에도 소켓이 있네?" 싶었는데, 같은 소켓이 아닙니다. TCP 소켓은 **연결 하나**를 뜻하고, UDP 소켓은 그냥 **포트 하나**입니다. 누가 보내든 다 받습니다.

매 패킷이 독립된 편지라서 앞뒤 맥락이 없습니다. 그래서 상대 주소도 매번 봉투에서 꺼내 읽어야 합니다.

---

## 클라이언트 쪽은 어떻게 다른가

한동안 "UDP는 소켓이 필요 없는 거 아닌가" 생각했습니다. 아니었습니다. **둘 다 소켓은 만듭니다. 차이는 연결을 하느냐입니다.**

TCP 클라이언트는 이 한 줄 안에서 두 가지 일을 합니다.

```java
Socket socket = new Socket("127.0.0.1", 9000);
```

```
  클라이언트                                        서버
      │                                             │
  ① 소켓 생성   OS 가 안 쓰는 포트를 골라준다 → 61105       │
      │                                             │
  ② connect — 여기서 handshake                       │
      │ ────────── SYN ───────────────────────────▶ │
      │ ◀───────── SYN + ACK ────────────────────── │
      │ ────────── ACK ───────────────────────────▶ │
      │                                             │
  ③ 소켓이 상대를 기억한다   "나는 9000번 전용"             │
      │                                             │
      │ ── write("hello") ───────────────────────▶  │   주소를 안 적는다
```

UDP는 생성자에 주소를 주지 않습니다.

```java
DatagramSocket socket = new DatagramSocket();
socket.send(new DatagramPacket(data, data.length, addr, 9001));
```

```
  클라이언트                                        서버
      │                                             │
  ① 소켓 생성   OS 가 포트를 골라준다 → 54321             │
      │         여기서 끝.  연결 과정이 없다              │
      │                                             │
  ② 보낼 때마다 봉투에 주소를 적는다                       │
      │   ┌─────────────────────────┐               │
      │   │ 받는이: 127.0.0.1:9001   │               │
      │   │ 내용:   "hello"          │ ───────────▶  │
      │   └─────────────────────────┘               │
```

그래서 소켓 하나로 할 수 있는 일이 달라집니다.

```
  TCP 소켓                           UDP 소켓
  ┌──────┐                         ┌──────┐
  │ 소켓  │──── 서버 A 전용 ────▶     │ 소켓  │───▶ 서버 A
  └──────┘                         │      │───▶ 서버 B
                                   │      │───▶ 서버 C
  서버 B 에도 보내려면                  └──────┘
  소켓을 또 만들어야 한다              소켓 하나로 다 보낸다
```

`netstat`에도 그대로 나옵니다.

```
 tcp4   127.0.0.1.61105   127.0.0.1.9000   ESTABLISHED
                          └──────────────┘  상대가 적혀 있다

 udp4   *.54321           *.*
                          └─┘              상대가 비어 있다
```

같은 "소켓"인데 한쪽은 상대가 있고 한쪽은 없습니다. UDP 소켓은 연결이 아니라 **내 쪽 출입구 하나**입니다.

```
 소켓   내 쪽 출입구            TCP · UDP 둘 다 있다
 연결   상대와 맺은 전용 통로     TCP 에만 있다
```

제가 헷갈렸던 건 소켓과 연결을 같은 것으로 보고 있었기 때문이었습니다.

> UDP에도 `socket.connect(addr, port)` 가 있긴 합니다. 그런데 handshake를 하는 게 아니라 "이 주소로만 주고받겠다"는 내 쪽 필터일 뿐입니다. 패킷은 하나도 안 나갑니다.

## 서버가 꺼져 있어도 "성공"한다

서버를 끄고 보내봤습니다.

```bash
nc -u 127.0.0.1 9001
hello
```

아무 일도 안 일어납니다. 에러도 없고 그냥 조용합니다.

TCP는 이렇습니다.

```bash
nc 127.0.0.1 9000        # 서버 꺼진 상태
```

```
nc: connectx to 127.0.0.1 port 9000 failed: Connection refused
```

```
 TCP    연결을 먼저 맺으니까   →  상대가 없으면 그 자리에서 안다
 UDP    그냥 던지니까         →  상대가 있는지조차 모른다
```

비연결형(connectionless)이라는 말이 이 뜻이었습니다. 보낸 건 성공했는데 받은 사람이 있는지는 모르는 상태요.

## 30,000개를 보내봤습니다

번호를 붙여 대량으로 보내고 몇 개가 도착했는지 세는 코드를 짰습니다.

```java
try (DatagramSocket client = new DatagramSocket()) {
    for (int i = 1; i <= total; i++) {
        byte[] data = String.valueOf(i).getBytes(UTF_8);
        client.send(new DatagramPacket(data, data.length, addr, PORT));
        // send() 는 "보냈다"만 알려준다. "도착했다"가 아니다
    }
}
```

받는 쪽 버퍼는 일부러 작게 잡았습니다.

```java
server.setReceiveBufferSize(8 * 1024);
```

```bash
java UdpLossTest.java 30000
```

```
┌──────────────────────────────────────┐
│  보낸 패킷   :     30,000              │
│  받은 패킷   :     29,260              │
│  유실        :        740  (2.47%)    │
│  전송 소요   :        107 ms           │
└──────────────────────────────────────┘

유실된 번호 예시: 5384 5385 5388 7240 7242 7243 ...
```

`send()`는 30,000번 다 성공했습니다. 도착한 건 29,260개고요. **같은 컴퓨터 안, 루프백인데 2.47%가 사라졌습니다.**

---

## 왜 사라졌나

랜선도 라우터도 거치지 않았는데 없어졌습니다. 범인은 수신 버퍼였습니다.

```
   보내는 쪽                            받는 쪽
   30,000개를 107ms 에  ─────────────▶  수신 버퍼 (8KB)
   쏟아붓는다                               │
                                           │  앱이 하나씩 꺼내 처리
                                           ▼
                                   처리 속도 < 도착 속도
                                           │
                                     버퍼가 가득 찬다
                                           │
                                   넘치는 건 그냥 버린다
```

버퍼가 꽉 차면 그다음 패킷은 갈 곳이 없습니다. 그래서 버립니다. 알려주지도 않습니다.

TCP였다면 헤더의 `win` 필드로 **"나 지금 버퍼 꽉 찼으니 천천히 보내"** 라고 말합니다. 보내는 쪽이 속도를 줄이고요. 이걸 흐름 제어라고 하는데, UDP 헤더에는 그 칸이 없습니다.

유실된 번호가 `5384 5385 5388`처럼 뭉쳐 나오는 것도 같은 이유입니다. 버퍼가 꽉 찬 그 순간에 도착한 것들이 한꺼번에 버려진 겁니다.

---

## 그럼 UDP는 왜 쓰나

여기까지 보면 UDP를 쓸 이유가 없어 보이는데, 판단 기준이 두 개 있었습니다.

```
 ① 늦게 도착한 데이터가 아직 쓸모 있나?
 ② 하나 빠지면 치명적인가?
```

```
                      늦은 데이터       빠진 데이터        선택
 ─────────────────────────────────────────────────────────────
 영상 통화             쓸모없다          티도 안 난다       UDP
 온라인 게임 좌표       쓸모없다          다음 게 온다       UDP
 DNS 조회             —               다시 물으면 된다    UDP
 파일 다운로드          여전히 필요       파일이 깨진다      TCP
 결제                 여전히 필요        큰일 난다         TCP
```

영상 통화에서 0.5초 전 프레임이 재전송되어 도착하면 오히려 방해입니다. 게임도 마찬가지로 지난 좌표는 의미가 없습니다. 이럴 땐 **빠진 걸 메우는 것보다 그냥 다음 걸 받는 게 낫습니다.**

TCP에는 더 성가신 문제도 있습니다.

```
 TCP   ①②③④⑤ 중 ③이 유실되면
       ④⑤가 이미 도착해 있어도 앱에 올려보내지 않는다
       ③이 재전송돼 도착할 때까지 전부 대기   ← 화면이 멈춘다

 UDP   ③이 유실되면 그냥 ④⑤를 처리한다       ← 화면이 잠깐 깨지고 넘어간다
```

순서를 보장하려다 보니 하나가 막히면 뒤가 다 밀립니다. 이걸 head-of-line blocking이라고 합니다. 통화 중에 화면이 멈추는 것보다 한 프레임 깨지는 게 나으니까 UDP를 쓰는 겁니다.

HTTP/3가 TCP를 버리고 UDP로 간 이유도 여기에 있습니다.

## 정리하면

```
                  TCP                      UDP
 ───────────────────────────────────────────────────────────
 연결              3-way handshake          없다
 도착 보장          ACK + 재전송              없다
 순서 보장          순서번호                  없다
 속도 조절          흐름 제어 (win)           없다
 헤더              20 bytes                 8 bytes
 쓰는 곳           파일, 결제, 웹            통화, 게임, DNS
```

외울 때는 "UDP는 기능이 없다"로 알고 있었는데, 헤더를 보고 나니 **없는 게 아니라 적을 칸을 안 만든 것**이었습니다. 빠른 이유도 거기 있고요.

그리고 루프백에서도 2%가 사라진다는 게 제일 의외였습니다. 네트워크가 멀쩡해도 받는 쪽이 못 따라가면 그냥 버려집니다.
