SYN → SYN+ACK → ACK. 그림으로는 수없이 봤는데 실제로 찍어본 적은 없었습니다.
Wireshark 없이 터미널만으로 한 번 보기로 했습니다.

## 전체 흐름

```
  클라이언트                                              서버
      │                                                   │
      │                                        ServerSocket(9000)
   CLOSED                                             LISTEN
      │                                                   │
      │ ─────────── SYN ────────────────────────────────▶ │   연결하자
      │ ◀────────── SYN + ACK ─────────────────────────── │   그래, 나도
      │ ─────────── ACK ────────────────────────────────▶ │   알겠다
      │                                                   │
  ESTABLISHED                                        ESTABLISHED
      │                                                   │
      │ ─────────── "hello" ────────────────────────────▶ │
      │ ◀────────── ack ───────────────────────────────── │
      │ ◀────────── "ECHO: hello" ─────────────────────── │
      │ ─────────── ack ────────────────────────────────▶ │
      │                                                   │
      │ ─────────── FIN ────────────────────────────────▶ │   나는 끝
      │ ◀────────── ACK ───────────────────────────────── │   알겠다
      │ ◀────────── FIN ───────────────────────────────── │   나도 끝
      │ ─────────── ACK ────────────────────────────────▶ │   알겠다
      │                                                   │
  TIME_WAIT                                            CLOSED
```

## 준비물은 에코 서버 하나

받은 문자열을 그대로 돌려주는 서버입니다.

```java
public class TcpEchoServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket serverSocket = new ServerSocket(9000)) {
            while (true) {
                Socket client = serverSocket.accept();   // 연결이 올 때까지 멈춤
                handle(client);
            }
        }
    }
}
```

```bash
java TcpEchoServer.java      # Java 11부터는 단일 파일로 바로 실행됩니다
```

`ServerSocket`과 `Socket`을 같은 걸로 알고 있었는데 역할이 다릅니다.

```
 ServerSocket   연결 요청을 받는 창구.  포트 하나에 하나
 Socket         실제 연결 하나.  손님마다 하나씩 생긴다
```

## handshake 찍기

터미널을 두 개 더 엽니다.

```bash
sudo tcpdump -i lo0 -n port 9000     # 패킷 구경
nc 127.0.0.1 9000                    # 접속
```

접속하자마자 세 줄이 올라옵니다.

```
IP 127.0.0.1.61105 > 127.0.0.1.9000: Flags [S],  seq 1234567890
IP 127.0.0.1.9000 > 127.0.0.1.61105: Flags [S.], seq 987654321, ack 1234567891
IP 127.0.0.1.61105 > 127.0.0.1.9000: Flags [.],  ack 1
```

교과서 그림이 그대로 찍혔습니다. 한 줄은 이렇게 읽습니다.

```
 IP 127.0.0.1.61105 > 127.0.0.1.9000: Flags [S], seq 1234567890
    └─── 출발 ────┘   └─── 도착 ───┘        │         │
         IP.포트          IP.포트          플래그    순서번호
```

플래그는 이 정도만 알면 읽힙니다.

```
 [S]    SYN         연결 요청
 [S.]   SYN + ACK   연결 수락
 [.]    ACK         확인 응답
 [P.]   PSH + ACK   데이터 전송
 [F.]   FIN + ACK   종료 요청
 [R]    RST         강제 끊김
```

`.` 이 ACK를 뜻합니다. 그래서 두 번째 줄 `[S.]`는 SYN과 ACK가 한 패킷에 같이 들어간 겁니다.

## 데이터를 보낼 때마다 확인이 온다

`hello`를 입력하면 패킷이 네 개 오갑니다.

```
 클라 → 서버    [P.]  length 6      "hello\n"
 서버 → 클라    [.]   ack 7         받았다
 서버 → 클라    [P.]  length 12     "ECHO: hello\n"
 클라 → 서버    [.]   ack 13        받았다
```

보낸 쪽은 ACK가 올 때까지 기다리고, 안 오면 다시 보냅니다. "TCP는 신뢰성이 있다"는 말의 실체가 이겁니다.

데이터 패킷이 `[P]`가 아니라 `[P.]`인 것도 이유가 있습니다.

```
 보낼 데이터가 있다  +  직전에 받은 것도 확인해줘야 한다
        └──────────── 한 패킷에 같이 실어 보낸다
```

ACK만 따로 보내면 패킷 수가 두 배가 되니까, 보낼 게 있을 때 묻어 보냅니다.

이 시점에 `netstat`을 다시 보면 줄이 세 개로 늘어 있습니다.

```
tcp4   0   0   127.0.0.1.9000    127.0.0.1.61105   ESTABLISHED
tcp4   0   0   127.0.0.1.61105   127.0.0.1.9000    ESTABLISHED
tcp4   0   0   *.9000            *.*               LISTEN
```

연결 하나에 양쪽 끝이 각각 한 줄씩 올라오고, `LISTEN`은 다음 손님을 위해 그대로 남습니다.

## 끊을 때는 왜 네 번인가

열 때는 세 번인데 닫을 때는 네 번입니다. TCP가 양방향이기 때문입니다.

```
 TCP 연결 하나
     ├─  클라이언트 → 서버   방향
     └─  서버 → 클라이언트   방향      파이프가 두 개다
```

파이프가 두 개니까 각각 따로 닫아야 합니다. 클라이언트가 FIN을 보낸 건 "내가 보낼 건 끝났다"는 뜻이지 "서버도 끝내라"는 뜻이 아닙니다.

상태 이름까지 붙이면 이렇게 됩니다.

```
  클라이언트                              서버
  ESTABLISHED                        ESTABLISHED
      │                                   │
      │ ──── ① FIN ─────────────────────▶ │
  FIN_WAIT_1                         CLOSE_WAIT
      │                                   │
      │ ◀─── ② ACK ────────────────────── │
  FIN_WAIT_2                              │  ← 서버는 여기서 더 보낼 수 있다
      │                                   │
      │ ◀─── ③ FIN ────────────────────── │
      │                               LAST_ACK
  TIME_WAIT                               │
      │ ──── ④ ACK ─────────────────────▶ │
      │                                CLOSED
  (1~2분 대기)
   CLOSED
```

서버가 ②와 ③을 합치지 못하는 이유가 `CLOSE_WAIT`이라는 이름에 그대로 들어 있습니다. "닫기를 기다리는 중" — 클라이언트는 끝났지만 서버는 보내던 걸 마저 보내야 하니까요. 열 때 SYN과 ACK를 합칠 수 있었던 건 양쪽 다 열겠다는 의사가 확실했기 때문입니다.

---

## 끊었는데 안 사라진다

종료 후에 `netstat`을 보면 `TIME_WAIT`이 남아 있습니다. 먼저 끊은 쪽에 1~2분 정도요. 처음엔 버그인 줄 알았습니다.

```
 ④번 ACK 가 중간에 유실되면?      서버는 ③번 FIN 을 다시 보낸다
 그때 내 소켓이 이미 없다면?       받아줄 쪽이 없어서 RST 가 날아간다
```

혹시 몰라서 잠깐 남겨두는 겁니다. 서버를 껐다 바로 켤 때 `Address already in use`가 뜨는 것도 이것 때문입니다.

---

## 정리하면

연결은 세 번에 열리고 네 번에 닫힙니다. 열 때는 둘 다 열겠다는 의사가 분명해서 가운데 두 패킷을 합칠 수 있고, 닫을 때는 방향마다 따로 닫아야 해서 합칠 수 없습니다.

`TIME_WAIT`도 그림으로 봤을 땐 그냥 지나쳤는데, 직접 `netstat`에 남아 있는 걸 보고 나니 왜 필요한지가 분명해졌습니다. 그림 백 번 보는 것보다 로그 세 줄 보는 게 빨랐습니다.
