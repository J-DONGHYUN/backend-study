HTTPS를 써야 한다는 건 알고 있었습니다. 안 쓰면 "위험하다"는 것도요.
그런데 정확히 뭐가 어떻게 보이는지는 본 적이 없어서, 서버를 띄워놓고 제 비밀번호를 직접 들여다봤습니다.

---

## 로그인 서버 하나 띄우기

JSON을 받아서 응답하는 서버입니다. 스프링 없이 JDK 내장 `HttpServer`로 만들었습니다.

```bash
java HttpLoginServer.java        # 8080 포트
```

패킷을 글자로 보려면 `-A` 옵션이 필요합니다.

```bash
sudo tcpdump -i lo0 -n -A 'tcp port 8080'
```

```
 -A   패킷 내용을 ASCII 로 출력    ← 이게 핵심
 -n   주소를 숫자 그대로
```

---

## 로그인 요청 하나

```bash
curl -X POST http://127.0.0.1:8080/login \
  -H "Content-Type: application/json" \
  -d '{"username":"donghyun","password":"MySecret1234"}'
```

tcpdump 쪽에 이게 올라옵니다.

```
POST /login HTTP/1.1
Host: 127.0.0.1:8080
User-Agent: curl/8.4.0
Content-Type: application/json
Content-Length: 48

{"username":"donghyun","password":"MySecret1234"}
                                    ▲
                            그대로 보입니다
```

헤더부터 본문까지 전부 읽힙니다. 암호도 뭣도 아니고 그냥 글자입니다. HTTP가 **텍스트 기반 프로토콜**이라는 말이 이런 뜻이었습니다.

응답도 똑같이 보입니다. 세션 쿠키를 내려주는 응답이었다면 그것도 같이 보였을 겁니다.

---

## HTTPS로 바꾸는 데 필요한 건 10줄

같은 서버에 TLS만 얹었습니다. **HTTP 처리 코드는 한 줄도 안 건드렸습니다.**

```java
KeyStore keyStore = ...load("keystore.p12")     // 개인키 + 인증서
SSLContext sslContext = ...init(keyManagers)    // TLS 엔진
server.setHttpsConfigurator(...)                // 서버에 장착
```

`keystore.p12`는 **개인키와 인증서를 담아둔 금고 파일**입니다. 실습이라 직접 만들었습니다.

```bash
keytool -genkeypair -alias lab \
  -storetype PKCS12 -keystore keystore.p12 -storepass labpass ...
```

이게 이 실습에서 제일 와닿았던 부분입니다.

```
 HTTP                       HTTPS
 ┌──────────┐              ┌──────────┐
 │  HTTP    │              │  HTTP    │   ← 똑같다. 안 바뀐다
 ├──────────┤              ├──────────┤
 │          │              │  TLS     │   ← 여기가 끼었다
 │  TCP     │              ├──────────┤
 │          │              │  TCP     │
 └──────────┘              └──────────┘
```

**HTTPS는 새로운 프로토콜이 아닙니다.** HTTP와 TCP 사이에 TLS라는 층이 하나 들어간 것뿐입니다. 그래서 컨트롤러 코드가 안 바뀝니다.

## 같은 자리를 다시 캡처

```bash
sudo tcpdump -i lo0 -n -A 'tcp port 8443'
```

```bash
curl -k -X POST https://127.0.0.1:8443/login \
  -H "Content-Type: application/json" \
  -d '{"username":"donghyun","password":"MySecret1234"}'
```

```
IP 127.0.0.1.52841 > 127.0.0.1.8443: Flags [P.], length 517
.....z.=.?.$..j...q.....9..8..5....
...6..*...?..v.(..}.....|..{.....k..j
                ▲
            알아볼 수 없는 바이트뿐입니다
```

`password`라는 글자가 어디에도 없습니다. 같은 요청, 같은 도구, 같은 컴퓨터인데요.

---

## 그런데 이건 여전히 보입니다

암호화해도 전부 가려지는 건 아니었습니다.

```
IP 127.0.0.1.52841 > 127.0.0.1.8443: Flags [P.], length 517
   └─ 출발 IP/포트 ─┘  └─ 도착 IP/포트 ─┘             └ 크기 ┘
          평문              평문                      평문
```

```
 가려지는 것       URL 경로, 헤더, 쿠키, 요청 본문, 응답 본문
 안 가려지는 것     출발·도착 IP, 포트, 패킷 크기, 접속 시각
```

IP와 포트는 가릴 수가 없습니다. 그게 암호화되면 **라우터가 어디로 보낼지 모르니까요.** 봉투 안은 봉인해도 주소는 겉에 적어야 하는 것과 같습니다.

그래서 "누가 어느 서버에 접속했는지"는 여전히 알 수 있습니다. 내용만 모를 뿐이죠.

---

## TLS는 언제 끼어드나

3-way handshake가 끝난 **다음**입니다. TCP 연결이 있어야 TLS도 할 수 있으니까요.

```
  클라이언트                                      서버
      │ ── SYN ──────────────────────────────▶ │
      │ ◀─ SYN + ACK ───────────────────────── │   TCP 3-way
      │ ── ACK ──────────────────────────────▶ │
      │                                        │
      │ ── ClientHello ─────────────────────▶  │   쓸 수 있는 암호 방식 목록
      │ ◀─ ServerHello + 인증서 ──────────────  │   이걸로 하자 + 내 인증서
      │                                        │
   인증서 검증                                   │
   (발급 기관이 믿을 만한가)                       │
      │                                        │
      │ ── 키 교환 ─────────────────────────▶  │   양쪽이 같은 대칭키를 만든다
      │ ◀─ Finished ───────────────────────── │
      │                                        │
      │ ═══ 여기부터 전부 암호화 ═════════════▶  │   POST /login ...
```

연결 하나 맺는 데 왕복이 더 늘어납니다. HTTPS가 HTTP보다 처음 접속이 느린 이유가 이겁니다.

키 교환 단계에서 재미있는 건, **비밀번호 같은 걸 주고받지 않는데도 양쪽이 같은 대칭키를 갖게 된다**는 점입니다. 중간에서 전부 엿들어도 그 키는 계산할 수 없습니다.

```
 인증서 검증·키 교환    비대칭키 (느리다)       연결할 때 한 번만
 실제 데이터 전송       대칭키 (빠르다)         그 뒤로 계속
```

비대칭키만 쓰면 느리고, 대칭키만 쓰면 키를 안전하게 건넬 방법이 없습니다. 그래서 **앞부분만 비대칭으로 하고 나머지는 대칭으로** 넘깁니다.

---

## TLS가 하는 일은 세 가지

암호화만 하는 게 아니었습니다.

```
 ① 암호화     남이 봐도 내용을 모른다
 ② 인증       접속한 서버가 진짜 그 서버인가        ← 인증서가 하는 일
 ③ 무결성     중간에서 내용을 바꾸면 들통난다
```

②가 없으면 암호화가 소용없습니다. 가짜 서버와 안전하게 통신하는 꼴이 되니까요. 인증서는 "이 도메인은 내 것이 맞다"를 **제3자(인증 기관)가 보증**해주는 문서입니다.

실습에서 `curl -k`를 붙인 것도 이것 때문입니다. 제가 직접 만든 인증서라 보증해줄 기관이 없어서, curl이 기본적으로 거부합니다.

---

## 개발자도구에선 왜 평문으로 보이나

HTTPS 사이트인데 개발자도구 Network 탭에는 요청 본문이 그대로 보입니다. 이게 한동안 이상했습니다.

```
  브라우저 안          { username, password }      ← 개발자도구가 보는 곳
       │                    암호화 전
       ▼
  ─────── 선 위 ──────  .....z.=.?.$..j...       ← tcpdump 가 보는 곳
       │
       ▼
  서버 안             { username, password }      ← 서버 로그가 보는 곳
                          복호화 후
```

**보는 지점이 다를 뿐입니다.** 개발자도구는 내 브라우저 안에서 암호화되기 전을 보여주고, tcpdump는 선 위를 지나가는 걸 봅니다. 둘 다 맞습니다.

프론트에서 `fetch`로 비밀번호를 보낼 때 따로 암호화 코드를 안 짜도 되는 이유도 같습니다. **브라우저가 TLS 층에서 알아서 처리**하고 올려보냅니다.

## 정리하면

```
              HTTP                      HTTPS
 ────────────────────────────────────────────────────────
 포트           80                        443
 구조           HTTP + TCP                HTTP + TLS + TCP
 패킷 내용       글자 그대로                 알아볼 수 없는 바이트
 가려지는 것      없음                      경로·헤더·쿠키·본문
 안 가려지는 것   —                        IP·포트·크기·시각
 첫 접속        3-way                     3-way + TLS handshake
```

직접 보기 전에는 "HTTPS 안 쓰면 위험하다"가 그냥 구호 같았습니다. 제 비밀번호가 터미널에 글자로 찍히는 걸 보고 나니 다르게 와닿았습니다.

그리고 HTTPS가 HTTP를 대체하는 게 아니라 **아래에 층을 하나 끼운 것**이라는 게 코드로 증명됐습니다. 10줄을 추가했는데 요청 처리 코드는 한 줄도 안 바뀌었으니까요.
